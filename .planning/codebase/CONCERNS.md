# CONCERNS
> Generated by codebase mapper | Focus: concerns

## Summary

The codebase has a clean core architecture but suffers from structural bloat (dead frontend directory, misplaced test files), security gaps (no file upload size limits, pickle deserialization from Redis, CORS wide open), and insufficient automated test coverage (only deduplicator and normalizer have unit tests; loader, metrics, cache, and router have zero). Memory pressure from unbounded xlsx file uploads processed entirely in-memory is the primary scalability risk.

---

## Critical

### Pickle Deserialization from Redis (Security / RCE Risk)

- **Issue:** `routers/analysis.py` line 72 calls `pickle.loads(cached_pickle)` on data retrieved from Redis. If Redis is compromised or an attacker gains write access, arbitrary code execution is possible via crafted pickle payloads.
- **Files:** `routers/analysis.py` (lines 70-72), `esoccer_dashboard/services/cache.py` (lines 81-91)
- **Impact:** Remote code execution on the API server if Redis is compromised.
- **Fix approach:** Replace pickle serialization with a safe format (Parquet bytes via `df.to_parquet()` / `pd.read_parquet()`). Parquet is also more compact and faster than pickle for DataFrames.

### No File Upload Size Limit

- **Issue:** The `POST /analyze` endpoint accepts unlimited file uploads with no size validation. An attacker (or accidental large file) can exhaust server memory since all file contents are read into memory (`await uf.read()`) and then processed by pandas.
- **Files:** `routers/analysis.py` (lines 248-252), `main.py` (no middleware for body limits)
- **Impact:** Denial of service via memory exhaustion. A single request with a 500MB xlsx can crash the container.
- **Fix approach:** Add a max file size check per file (e.g., 50MB) and a max total upload size. FastAPI does not enforce this by default. Add validation after `await uf.read()` or configure uvicorn `--limit-concurrency` and a reverse proxy limit. Example:
  ```python
  MAX_FILE_SIZE = 50 * 1024 * 1024  # 50MB
  for uf in files:
      content = await uf.read()
      if len(content) > MAX_FILE_SIZE:
          raise HTTPException(413, f"File '{uf.filename}' exceeds 50MB limit")
  ```

### CORS Allows All Origins

- **Issue:** `main.py` line 17-21 sets `allow_origins=["*"]`, `allow_methods=["*"]`, `allow_headers=["*"]`. This means any website can make authenticated requests to the API if a user's browser has the API key.
- **Files:** `main.py` (lines 16-21)
- **Impact:** Cross-site request forgery for any client that stores the API key in a browser context. Since auth is via header (not cookie), real-world risk is moderate, but it violates principle of least privilege.
- **Fix approach:** Restrict `allow_origins` to the actual frontend domain (`dash-tg.arvsystems.cloud`) via environment variable. Keep `["*"]` only for local development.

### `.env.prod` Committed to Git

- **Issue:** `.gitignore` explicitly allows `.env.prod` (`!.env.prod`), and the file exists in the repository. Production environment files should never be in version control, even if they currently contain non-secret values, because secrets may be added later.
- **Files:** `.env.prod`, `.gitignore` (line 22)
- **Impact:** If `API_KEYS` or other secrets are added to `.env.prod`, they become part of git history permanently.
- **Fix approach:** Remove `.env.prod` from the repo, add it to `.gitignore` without the `!` exception, and pass production config via Docker Swarm secrets or CI/CD environment variables (which `docker-compose.prod.yml` already partially does with `${API_KEYS}`).

## Moderate

### No File Type/Content Validation on Uploads

- **Issue:** The `/analyze` endpoint does not verify that uploaded files are actually `.xlsx` files. A user could upload any file (e.g., a 100MB ZIP) and it would be passed to `pd.read_excel()` which may behave unpredictably or raise unclear errors.
- **Files:** `routers/analysis.py` (lines 239-252)
- **Impact:** Confusing error messages for users; potential for unexpected pandas behavior on malformed files. `openpyxl` could hang on specially crafted files.
- **Fix approach:** Validate file extension (`.xlsx`) and optionally check magic bytes (`PK\x03\x04` for ZIP-based xlsx) before processing.

### Dead Frontend Directory (`esoccerdashboard/`)

- **Issue:** A full Next.js/Vite frontend application exists at `esoccerdashboard/` inside the backend repository. It has its own `package.json`, `Dockerfile`, `node_modules/` (gitignored), and source code. This is a separate application that should live in its own repository or at minimum be clearly separated.
- **Files:** `esoccerdashboard/` (entire directory), `esoccerdashboard/package.json`, `esoccerdashboard/Dockerfile`
- **Impact:** Increases Docker build context size (even with `.dockerignore`), confuses contributors about repo boundaries, and the backend `Dockerfile` copies everything (`COPY . /app`) which includes this frontend code in the API image.
- **Fix approach:** Either (a) move `esoccerdashboard/` to its own repository, or (b) add it to the backend `.dockerignore` to prevent it from bloating the API Docker image. Also add `esoccerdashboard/` to the backend `.dockerignore`.

### Leftover Streamlit Configuration (`.streamlit/`)

- **Issue:** A `.streamlit/` directory with `config.toml` exists, suggesting the project was previously a Streamlit app. This is dead code/config that adds confusion.
- **Files:** `.streamlit/config.toml`
- **Impact:** Minor confusion for new developers.
- **Fix approach:** Remove `.streamlit/` directory entirely.

### Test Files at Root Level

- **Issue:** `test_api.py` and `test_api2.py` are integration test scripts placed at the project root. They use hardcoded local file paths (`C:\Users\Bruno\Desktop\...`) and hardcoded API keys (`"123"`), making them non-portable and non-automatable.
- **Files:** `test_api.py`, `test_api2.py`
- **Impact:** Tests cannot run in CI or on any machine besides the original developer's. They are not discoverable by pytest. They contain hardcoded credentials.
- **Fix approach:** Move to `tests/` directory, use pytest fixtures, use environment variables for paths and API keys, and mock or use test data fixtures instead of real xlsx files.

### No Rate Limiting

- **Issue:** The API has no rate limiting. A client can send unlimited `/analyze` requests, each potentially triggering a full pandas pipeline on large xlsx files.
- **Files:** `main.py`, `routers/analysis.py`
- **Impact:** A single client (or attacker with a valid API key) can monopolize server resources. The cache mitigates repeated identical requests, but different file combinations bypass cache.
- **Fix approach:** Add rate limiting middleware (e.g., `slowapi` or custom middleware) with per-API-key limits. A reasonable default: 10 requests/minute for `/analyze`.

### Redis Has No Authentication

- **Issue:** Redis in both `docker-compose.yml` and `docker-compose.prod.yml` runs without a password. In production, Redis is exposed on the Docker network without auth.
- **Files:** `docker-compose.yml` (lines 14-18), `docker-compose.prod.yml` (lines 42-55)
- **Impact:** Any service on the same Docker network can read/write Redis data, including cached analysis results and pickled DataFrames.
- **Fix approach:** Add `--requirepass` to the Redis command in production compose and update `REDIS_URL` to include the password.

### Blueprint Storage Stores Full Dataset in Redis

- **Issue:** `store_blueprint()` serializes the entire deduplicated DataFrame as JSON and stores it in Redis with 24h TTL. For large datasets (16k+ rows), this can be several megabytes per analysis run.
- **Files:** `routers/analysis.py` (line 126-127), `esoccer_dashboard/services/cache.py` (lines 70-78)
- **Impact:** Redis memory usage grows quickly. Each analysis stores three keys: `analysis:`, `export:`, and `blueprint:`, with blueprint being the largest.
- **Fix approach:** Consider compressing blueprint data (gzip), reducing TTL, or storing blueprints on disk instead of Redis. Alternatively, store only the dedup metadata needed for the blueprint endpoint rather than the full DataFrame.

### `requirements.txt` Has No Pinned Versions

- **Issue:** All dependencies in `requirements.txt` are unpinned (e.g., `fastapi` not `fastapi==0.115.0`). Builds are not reproducible.
- **Files:** `requirements.txt`
- **Impact:** A new `pip install` may pull breaking changes in any dependency. pandas, numpy, and openpyxl are particularly risky as they have frequent breaking changes between major versions.
- **Fix approach:** Pin all dependencies with exact versions. Run `pip freeze > requirements.txt` from a known-good environment, or use `pip-tools` with a `requirements.in` file.

### MD5 Used for Cache Key Hashing

- **Issue:** `gerar_cache_key()` uses MD5 for cache key generation. While this is not a security-critical use (it is for cache identity, not authentication), MD5 has known collision vulnerabilities.
- **Files:** `esoccer_dashboard/services/cache.py` (lines 21-38), `routers/analysis.py` (line 69)
- **Impact:** Low practical risk for cache keys, but could cause cache poisoning if an attacker crafts colliding file contents. More importantly, it signals to auditors that the codebase uses deprecated cryptographic primitives.
- **Fix approach:** Replace with `hashlib.sha256()` for a negligible performance cost and better security posture.

## Minor

### Duplicate Documentation Files

- **Issue:** Both `CLAUDE.md` and `CLAUDE_v3_final.md` exist at the root. They appear to contain the same or similar content, creating ambiguity about which is authoritative.
- **Files:** `CLAUDE.md`, `CLAUDE_v3_final.md`
- **Impact:** Confusion about which document to follow.
- **Fix approach:** Remove `CLAUDE_v3_final.md` if `CLAUDE.md` is the active version.

### `GET /strategies` Has No Auth

- **Issue:** The `/strategies` endpoint does not require API key authentication, unlike all other endpoints. While the data is not sensitive, this is inconsistent.
- **Files:** `routers/analysis.py` (lines 177-191) -- note no `_key: AuthDep` parameter.
- **Impact:** Exposes strategy configuration publicly. Low severity since this is non-sensitive metadata.
- **Fix approach:** Add `_key: AuthDep` parameter for consistency, or document the intentional lack of auth.

### Synchronous Redis Calls in Async Handlers

- **Issue:** All Redis operations use the synchronous `redis-py` client (`redis.from_url()`) but are called from `async` FastAPI endpoints. This blocks the event loop during Redis I/O.
- **Files:** `esoccer_dashboard/services/cache.py` (all functions), `routers/analysis.py` (line 169)
- **Impact:** Under concurrent load, a slow Redis response blocks all other requests. For current low-traffic usage this is negligible, but it limits horizontal scaling on a single instance.
- **Fix approach:** Switch to `redis.asyncio` client or run synchronous Redis calls in a thread pool via `asyncio.to_thread()`.

### `compute()` Closure Raises HTTPException

- **Issue:** Inside `_analyze_with_strategy()`, the inner `compute()` function raises `HTTPException` (lines 89, 110). This function is passed to `get_or_compute()` as a callback. Raising HTTP exceptions from deep within the cache layer violates separation of concerns.
- **Files:** `routers/analysis.py` (lines 65-167)
- **Impact:** Cache layer becomes tightly coupled to HTTP error handling. If the cache layer is reused outside FastAPI (e.g., CLI tool), HTTPExceptions would be inappropriate.
- **Fix approach:** Raise domain-specific exceptions (e.g., `NoDataError`) from `compute()` and catch/translate them to HTTPException in the router.

### No Graceful Handling of Redis Connection Failure

- **Issue:** If Redis is down, the first API request will raise an unhandled `redis.ConnectionError`. Only the `/cache/status` endpoint wraps Redis calls in a try/except.
- **Files:** `esoccer_dashboard/services/cache.py` (line 17), `routers/analysis.py` (line 169)
- **Impact:** Any endpoint returns a 500 Internal Server Error with a raw traceback when Redis is unavailable.
- **Fix approach:** Add a middleware or dependency that catches `redis.ConnectionError` and returns a clear 503 response. Optionally, add a fallback mode that computes without caching when Redis is down.

### `_UploadFileAdapter` Duplicates Protocol

- **Issue:** `routers/analysis.py` defines `_UploadFileAdapter` to adapt FastAPI `UploadFile` to the `UploadedLike` protocol in `loader.py`. This is functional but creates an unnecessary wrapper class when the loader could accept bytes directly.
- **Files:** `routers/analysis.py` (lines 41-47), `esoccer_dashboard/services/loader.py` (lines 35-38)
- **Impact:** Minor code smell. The adapter exists because the loader was designed for Streamlit's file uploader interface (legacy from when this was a Streamlit app).
- **Fix approach:** Refactor `load_tips_enviadas()` to accept `list[tuple[str, bytes]]` directly, removing the need for the protocol and adapter.

### Test Coverage Gaps

- **What is not tested:** `esoccer_dashboard/services/loader.py`, `esoccer_dashboard/services/metrics.py`, `esoccer_dashboard/services/cache.py`, `routers/analysis.py`, `middleware/auth.py`
- **Files:** `tests/test_deduplicator.py` (3 tests), `tests/test_normalizer.py` (3 tests) -- only 6 unit tests total
- **Risk:** Core business logic in `metrics.py` (SRPT calculation, reds_after_red, streak counting, all 16 metrics) has zero test coverage. Regressions in metric calculations would go undetected.
- **Priority:** High. `metrics.py` contains the most complex business logic and should have comprehensive unit tests for each metric function (`_srpt`, `_reds_after_red`, `_max_streak`, `_trailing_streak`, `compute_metrics`).
